# День 7. Оценка уверенности и контроль качества инференса

CLI-приложение: LLM-инференс с явной оценкой уверенности и контролем приёмки
результата — без файнтюна. Домен, где ошибка недопустима: разбор свободных
русскоязычных платёжных поручений в структурный JSON `{amount, currency, recipient}`.
Неверное извлечение = неверное движение денег, поэтому неуверенные ответы
отклоняются и эскалируются человеку, а не угадываются.

Три подхода к контролю (задание требует ≥2, реализовано 3):

1. **Redundancy** — то же извлечение выполняется 3 раза при temperature 0.8,
   ответы сравниваются по канонической форме, побеждает большинство
   (3/3 → agreement 1.0; 2/3 → 0.67; нет большинства → провал);
2. **Constraint-based** — чистые проверки предметной области: сумма положительна,
   ≤ 2 знаков, ≤ 1 000 000; валюта ∈ {RUB, USD, EUR}; получатель непустой,
   не плейсхолдер, ≤ 100 символов;
3. **Self-check + scoring** — второй проход LLM (t=0.0, jsonMode): модель получает
   исходный текст и извлечённый JSON и возвращает `{status: OK|UNSURE|FAIL,
   confidence: 0..1, reason}`.

## Как устроено

```
текст поручения
      │
      ▼
┌────────────────────┐   3 вызова, t=0.8
│ RedundancyRunner   │──────────────────► голосование по канонической форме
└────────────────────┘
      │ большинства нет ──────────────► RETRY / REJECT (redundancy)
      ▼ majority-ответ
┌────────────────────┐   без I/O
│ ConstraintChecker  │
└────────────────────┘
      │ нарушения ────────────────────► RETRY / REJECT (constraints)
      ▼
┌────────────────────┐   1 вызов, t=0.0
│ SelfChecker        │──► {status, confidence, reason}
└────────────────────┘
      │
      ▼ правило приёмки
  OK/UNSURE ∧ conf ≥ 0.6 ∧ agreement ≥ 2/3 ─► ACCEPT
  иначе ────────────────────────────────────► RETRY ×1 (строгий промпт) → REJECT
```

Combined confidence = agreement × selfCheckConfidence — произведение независимых
оценок устойчивости к сэмплированию и корректности по мнению проверяющего прохода.

Файлы:

- `DeepSeekClient.kt` — тонкий клиент `/chat/completions`; возвращает `ChatResult`
  с usage-токенами и латентностью (для метрик цены контроля);
- `TransferOrder.kt` — DTO поручения + каноническая форма для голосования;
- `RedundancyRunner.kt` — подход №1: 3 извлечения + majority vote;
- `ConstraintChecker.kt` — подход №2: именованные нарушения, чистая функция;
- `SelfChecker.kt` — подход №3: самопроверка вторым проходом, оборонительный парсинг;
- `InferenceGate.kt` — оркестрация конвейера, retry, правило приёмки;
- `GateResult.kt`, `CallMetrics.kt` — sealed-вердикт и аккумулятор вызовов/токенов/мс;
- `TestCases.kt` — 12 кейсов: корректные / пограничные / шумные (по 4);
- `QualityRun.kt` — прогон, прогресс-лог, отчёт `output/report.md`
  с итогами и сравнением с single-shot baseline (фактический первый вызов кейса).

## Запуск

```bash
cp .env.example .env   # вписать DEEPSEEK_API_KEY

./run.sh run                                    # все 12 кейсов → output/report.md (~60 LLM-вызовов)
./run.sh one "Переведи 5000 рублей Ивану Петрову"  # один текст, подробный вердикт
./demo.sh                                       # сценарий для видео (DEMO_PAUSE=2 для пауз)
```

| Переменная | Дефолт | Зачем |
|------------|--------|-------|
| `DEEPSEEK_API_KEY` | — (обязателен) | ключ DeepSeek API |
| `DEEPSEEK_MODEL` | `deepseek-v4-flash` | модель для извлечения и самопроверки |
| `DEMO_PAUSE` | `0` | пауза между шагами demo.sh, сек |

## Чеклист задания

- [x] Инференс с оценкой уверенности без файнтюна — конвейер `InferenceGate`,
      combined confidence = agreement × self-check confidence;
- [x] ≥2 подхода контроля качества — реализовано три: redundancy (голосование 3×),
      constraint-based (жёсткие правила домена), self-check + scoring (второй проход LLM);
- [x] Контроль приёмки: ACCEPT / RETRY (одно повторное инференс-окно со строгим
      промптом) / REJECT с эскалацией человеку — sealed `GateResult`;
- [x] Проверка на корректных, пограничных и шумных данных — 12 кейсов в `TestCases.kt`
      (по 4 в группе: ясные поручения, неоднозначности, опечатки/не-поручения/инъекция);
- [x] Метрики: сколько отклонено, сколько потребовало re-inference, влияние на
      latency и cost — таблица и итоги в `output/report.md`, cost в множителе токенов
      против фактического single-shot baseline (первый вызов каждого кейса).
