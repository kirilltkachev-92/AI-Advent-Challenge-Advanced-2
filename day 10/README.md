# День 10. Micro-model first: проверка перед LLM

Двухуровневый инференс для классификации запросов клиентов в поддержку банка
(интенты: баланс, блокировка карты, возврат, перевод, смена пин-кода, оператор).
По умолчанию такие запросы гоняют через большую LLM, но большинство формулировок
тривиальны — их закрывает **уровень 1**: micro-model на чистом Kotlin (TF-IDF +
nearest centroid по seed-корпусу, без сети, без зависимостей), отвечающая за
сотни МИКРОсекунд. **Уровень 2** — большая LLM (DeepSeek) — вызывается ТОЛЬКО
когда micro-model честно говорит UNSURE.

Ключевое решение — откуда берётся уверенность. Спрашивать маленькую модель
«насколько ты уверена?» бесполезно: маленькие модели рапортуют о 100%
уверенности (эффект Даннинга–Крюгера). Поэтому уверенность здесь СТРУКТУРНАЯ:
`score = top1 · (1 + margin) / 2`, где top1 — косинусная близость к лучшему
центроиду, margin — отрыв от второго. UNSURE, если score ниже порога, top1 ниже
абсолютного пола или в запросе < 2 знакомых словарю токенов (OOV-защита от
сленга и опечаток).

## Как устроено

```
запрос клиента («какой у меня баланс», «закинь косарь брату», …)
      │
      ▼
Уровень 1: MicroClassifier — чистый Kotlin, БЕЗ сети (~0.3 мс)
токенизация + стемминг → TF-IDF-вектор → косинус к 6 центроидам
      │
      ├── статус OK (score ≥ порога, top1 ≥ пола, ≥2 знакомых токенов)
      │        └──► финальный интент, level=micro, 0 токенов LLM
      │
      └── статус UNSURE (низкая близость / малый отрыв / OOV)
               │
               ▼
        Уровень 2: LlmClassifier — DeepSeek, jsonMode, t=0.0 (~1.5 с)
        строгий выход {"intent":"BALANCE|…|OPERATOR"} → валидация по enum
               ├── валиден → финальный интент, level=llm
               ├── невалиден → 1 retry с указанием на ошибку
               └── снова невалиден → INVALID, безопасный дефолт OPERATOR
                   (неуверенный робот отдаёт клиента человеку, а не гадает)
```

Файлы:

- `Config.kt` — env + `.env`: ключ, модель fallback, порог уверенности;
- `Intent.kt` — enum из 6 интентов (UNSURE — статус маршрутизации, не интент);
- `Tokenizer.kt` — lowercase, ё→е, пунктуация → пробелы, лёгкий стемминг
  (срезание одного русского окончания, без библиотек);
- `IntentSeeds.kt` — seed-корпус: ~10 размеченных фраз на интент (включая сленг);
- `MicroClassifier.kt` — уровень 1: TF-IDF, центроиды, структурная уверенность;
- `DeepSeekClient.kt` — тонкий клиент `/chat/completions` на java.net.http,
  модель аргументом вызова, возвращает текст + usage-токены + латентность;
- `CallMetrics.kt` — аккумулятор вызовы/токены/мс (конвейер vs базлайн);
- `LlmClassifier.kt` — уровень 2 и он же all-LLM-базлайн: строгий JSON-контракт,
  retry, безопасный дефолт;
- `RouteResult.kt` — sealed-итог конвейера: кто дал метку (micro / llm) + цена;
- `TwoTierPipeline.kt` — маршрутизация: micro → при UNSURE fallback;
- `QueryCases.kt` — 30 размеченных запросов: 10 простых, 10 пограничных
  (сленг/опечатки), 10 трудных (простыни, отрицания, мульти-интент, инъекции);
- `SeriesRun.kt` — прогон серии, прогресс-строки, отчёт `output/report.md`;
- `Main.kt` — wiring и разбор команд `run` | `one` | `micro`.

## Запуск

```bash
cp .env.example .env   # вписать реальный DEEPSEEK_API_KEY
./run.sh run                            # 30 кейсов: конвейер + all-LLM-базлайн + output/report.md
./run.sh one "какой у меня баланс"      # один запрос подробно: близости, маршрут, fallback
./run.sh micro                          # вся серия только micro-model: офлайн, 0 LLM-вызовов
./demo.sh                               # сценарий для видео
```

| Переменная | Дефолт | Зачем |
|------------|--------|-------|
| `DEEPSEEK_API_KEY` | — (обязательна для `run`/`one`) | ключ DeepSeek; уровню 1 и команде `micro` не нужен |
| `FALLBACK_MODEL` | `deepseek-v4-flash` | модель уровня 2 (fallback и базлайн) |
| `CONFIDENCE_THRESHOLD` | `0.20` | порог score micro-model: ниже — уходим в fallback |
| `DEMO_PAUSE` | `0` | пауза между шагами demo.sh, сек |

Коммитится и эталонный `output/report.md` (исключение из правила «output/ не
коммитим»): demo.sh показывает его как кешированный прогон, README цитирует
его цифры. Результаты эталонного прогона (30 кейсов, `deepseek-v4-flash`): micro-model
закрыла 19/30 (63%), в fallback ушло 11; вызовы большой LLM срезаны с 30 до 11;
точность конвейера 30/30 — не хуже all-LLM-базлайна (30/30); средняя латентность
на кейс 567 мс против 1567 мс; токены 4946 против 13086 (экономия 62%).

## Чеклист задания

- [x] Уровень 1 — micro-model, обязательный вход: TF-IDF nearest-centroid на
      чистом Kotlin, всегда возвращает структурированный результат — метку enum
      `Intent` + score — и статус уверенности OK / UNSURE (`MicroResult`).
- [x] Уровень 2 — большая LLM только как fallback: вызывается ИСКЛЮЧИТЕЛЬНО при
      UNSURE (score ниже порога / top1 ниже пола / OOV); при невалидном формате
      ответа LLM — retry, затем безопасный дефолт OPERATOR (`LlmClassifier`).
- [x] Уверенность не самооценка модели, а структурная метрика
      (близость + отрыв top1−top2) — маленькие модели самоуверенны
      (Даннинг–Крюгер), их самоотчёту верить нельзя.
- [x] Тест на 30 запросах: 10 простых + 10 пограничных + 10 трудных
      (`QueryCases`), измерено: сколько закрыла micro-model (19/30), сколько
      ушло в fallback (11/30), всего вызовов большой LLM (11), средняя
      латентность (567 мс/кейс против 1567 мс у all-LLM) — `output/report.md`.
- [x] Сравнение с «как обычно»: параллельный all-LLM-базлайн на тех же кейсах —
      точность конвейера не упала (30/30 vs 30/30), при экономии 62% токенов
      и в ~2.8 раза меньшей средней латентности.
