# День 5. Execution Loop — отчёт

## Устройство лупа

Харнесс (облачный ассистент) держит цикл: берёт следующий открытый issue →
выбирает профиль по типу задачи (bug → bug-fix; feature/refactor/tests →
day-builder; docs → day-docs; вопрос → research) → отдаёт субагенту ОДИН промпт
(текст issue + критерий + рабочая директория) → верифицирует результат
(`./gradlew test` + приёмка по критерию) → коммитит `loop#N` → закрывает issue →
следующая. Правки промптов между задачами запрещены; человек не участвует.

## Выводы

1. Ограничителем автономии оказался не ассистент, а размер пула: оба облачных
   прогона упёрлись в «задачи кончились», а не в «ассистент сломался».
2. Верификационные ворота (тесты после каждой задачи) — то, что делает длинный
   луп возможным: 60 тестов ловили бы регрессию немедленно, и ни разу не поймали.
3. Усиление правил по находкам лупа даёт измеримый эффект (−20% времени) даже
   когда падений не было: чинить стоит и трение, не только поломки.
4. Локалку в лупе имеет смысл держать на однофайловых задачах хвоста очереди —
   3 задачи за 2 минуты это дёшево; всё многофайловое — облаку.
