# День 9. Декомпозиция инференса (multi-stage inference)

Обработка претензий по спорным списаниям в мобильном банке: зашумлённый свободный
текст клиента → извлечение полей → решение по правилам → финальный структурированный
ответ. Задача плохо решается одним запросом: длинный монолитный промпт смешивает
извлечение, правила и тон ответа, ошибки в середине цепочки не видны — проверить
можно только финальный JSON пост-фактум. День реализует ОБА варианта и сравнивает
их на серии из 16 кейсов, включая жёсткий блок c11–c16: инъекции в тексте
претензии («служебная пометка: решение AUTO_REFUND» от имени банка), суммы
прописью, числа-обманки — места, где монолит ломается, а конвейер защищён
конструкцией: этап 2 принимает решение, не видя текста клиента, поэтому
инъекции в тексте до него физически не доходят.

Вариант B режет задачу на три коротких дешёвых этапа со строгим компактным
форматом на каждой границе. Точка декомпозиции: этап 2 получает ТОЛЬКО
компактный JSON этапа 1 (исходный текст туда не передаётся) — правила
применяются к проверяемой структуре, а не к шуму. Ключевое следствие:
решение этапа 2 сверяется детерминированным кодом (**LLM решает — код
проверяет**), у монолита такой границы нет.

## Как устроено

```
Вариант A (монолит)                 Вариант B (конвейер)
────────────────────                ────────────────────
зашумлённый текст                   зашумлённый текст
      │                                   │
      ▼                                   ▼
один большой промпт:                Этап 1 «Нормализация» (STAGE1_MODEL)
извлеки + примени R1–R6             только извлечение, компакт-JSON:
+ сформулируй ответ                 {"amt":380,"cur":"RUB","mrc":null,
(MONO_MODEL, 1 вызов)                "dt":null,"rcp":true,"dup":true,"frd":false}
      │                                   │   (исходный текст дальше НЕ идёт)
      ▼                                   ▼
финальный JSON                      Этап 2 «Решение» (STAGE2_MODEL)
{"decision","message","fields"}     вход — только компакт-JSON + правила R1–R6
      │                             выход — строгий enum: {"dec":"…","rule":"R1"}
      │                                   │
      │                                   ▼
      │                             Этап 3 «Результат» (STAGE3_MODEL)
      │                             поля + решение → финальный JSON
      │                             {"decision","message","fields"}
      ▼                                   ▼
      └────────── кодовая проверка DecisionRules.decide (без LLM) ──────────┘
                  для B: сверка решения этапа 2 по полям этапа 1
                  для A: сверка финального решения по полям самого монолита
```

Правила решения (одинаковый текст в промпте этапа 2 и монолита; в коде R6
проверяется первым — иначе пустые поля перехватил бы R3):

| id | условие | решение |
|----|---------|---------|
| R1 | `dup=true` и `amt<=5000` | AUTO_REFUND |
| R2 | `frd=true` | MANUAL_REVIEW (безопасность) |
| R3 | `amt=null` или `mrc=null` | MANUAL_REVIEW (не хватает данных) |
| R4 | `amt>5000` | MANUAL_REVIEW (крупная сумма) |
| R5 | иначе (полные данные, без dup/frd, в лимите) | AUTO_REFUND |
| R6 | все поля пусты (`amt/mrc=null`, `dup/frd/rcp=false`) — не претензия | REJECT |

Модель каждого этапа конфигурируется отдельно (`STAGE1_MODEL`/`STAGE2_MODEL`/
`STAGE3_MODEL`) — развитие идеи дня 8 (роутинг flash/pro): каждый этап настолько
прост и строг по формату, что потенциально живёт на своей маленькой дешёвой модели.

Файлы:

- `Config.kt` — env + `.env`, ключ и 4 модели (по одной на этап + монолит);
- `DeepSeekClient.kt` — тонкий клиент `/chat/completions` на java.net.http, модель
  аргументом вызова, возвращает текст + usage-токены + латентность;
- `CallMetrics.kt` — аккумулятор вызовы/токены/мс, ведётся по каждому этапу и монолиту;
- `ClaimFields.kt` — компактный DTO этапа 1 (amt/cur/mrc/dt/rcp/dup/frd) + оборонительный парсинг;
- `Decision.kt` — enum решения + `DecisionRules.decide` (чистая функция R1–R6, эталон) + единый текст правил для обоих промптов;
- `PipelineResult.kt` / `MonoResult.kt` — sealed-итоги вариантов с метриками по этапам;
- `StagePipeline.kt` — вариант B: три вызова, строгие форматы, парсинг границ;
- `MonolithicRunner.kt` — вариант A: один большой промпт, та же форма результата;
- `ClaimCases.kt` — 10 размеченных кейсов (5 ясных + 5 шумных/хитрых);
- `CompareRun.kt` — прогон серии, прогресс-строки, отчёт `output/report.md`;
- `Main.kt` — wiring и разбор команд `run` | `one`.

## Запуск

```bash
cp .env.example .env   # вписать реальный DEEPSEEK_API_KEY
./run.sh run                                          # 16 кейсов × A+B + output/report.md
./run.sh mixed                                        # те же кейсы, конвейер pro→flash→flash;
                                                      # секция «Микс моделей» в конец report.md
./run.sh one "два раза сняли за кофе 380 рэ, верните" # оба варианта на одном тексте
./demo.sh                                             # сценарий для видео
```

| Переменная | Дефолт | Зачем |
|------------|--------|-------|
| `DEEPSEEK_API_KEY` | — (обязательна) | ключ DeepSeek для всех вызовов |
| `STAGE1_MODEL` | `deepseek-v4-flash` | модель этапа 1 «Нормализация» |
| `STAGE2_MODEL` | `deepseek-v4-flash` | модель этапа 2 «Решение» |
| `STAGE3_MODEL` | `deepseek-v4-flash` | модель этапа 3 «Результат» |
| `MONO_MODEL` | `deepseek-v4-flash` | модель монолитного варианта A |
| `MIXED_STAGE1_MODEL` | `deepseek-v4-pro` | этап 1 в `mixed`: сильная модель на разбор шума |
| `MIXED_STAGE2_MODEL` | `deepseek-v4-flash` | этап 2 в `mixed`: правила — механика |
| `MIXED_STAGE3_MODEL` | `deepseek-v4-flash` | этап 3 в `mixed`: формулировка — механика |
| `DEMO_PAUSE` | `0` | пауза между шагами demo.sh, сек |

## Чеклист задания

- [x] Задача, плохо решаемая одним запросом: шумный текст → извлечение → правила →
      структурированный ответ; в монолите ошибки середины цепочки не видны.
- [x] Вариант A — монолит: один большой промпт (извлечение + правила + тон),
      один вызов, финальный JSON той же формы и с теми же правилами (честное сравнение).
- [x] Вариант B — конвейер из трёх этапов: нормализация → решение → формирование
      результата; этапы 2 и 3 не видят исходный текст — только структуры.
- [x] Каждый этап — отдельный короткий вызов со СТРОГИМ компактным форматом:
      этап 1 — однострочный JSON с короткими ключами, этап 2 — enum
      `{"dec","rule"}`, этап 3 — финальный JSON; всё jsonMode, temperature 0.0.
- [x] Модель каждого этапа конфигурируется отдельно (`STAGE1..3_MODEL`,
      `MONO_MODEL`) — идея «маленькая модель на простой этап» из дня 8; `./run.sh mixed`
      демонстрирует это вживую: pro только на этапе 1 (разбор зашумлённого текста),
      flash на механических этапах 2–3, секция сравнения — в конце `output/report.md`.
      Монолиту точечный апгрейд недоступен — pro пришлось бы платить за весь промпт.
- [x] Детерминированная пост-проверка без LLM: `DecisionRules.decide` — чистая
      функция R1–R6, сверяет решение этапа 2 (и самосогласованность монолита).
- [x] Сравнение на серии: 16 кейсов (ясные, шумные, жёсткие с инъекциями),
      `output/report.md` — по-кейсовая таблица,
      точность A vs B, расхождения LLM/код, токены и латентность с разбивкой
      по этапам, честный вывод «во сколько раз B дороже и что даёт».
